# 14. Исключения и работа с отказами

## Обычный результат и невозможность продолжить

Исключение сообщает, что операция не завершилась обычным результатом. Throw создаёт переход управления к подходящему обработчику. Выполнение оставшихся инструкций текущего блока прекращается; если обработчика здесь нет, поиск поднимается по цепочке вызовов. Stack trace показывает тип, сообщение и места вызовов, но причина не всегда находится в последней строке приложения.

Исключение не должно заменять обычное ветвление для ожидаемого выбора. Отсутствие элемента может быть нормальным результатом поиска. Повреждённый файл обязательных данных может означать отказ загрузки. Сначала реши, что является договором операции.

## Checked и unchecked

RuntimeException и её потомки относятся к unchecked: компилятор не требует обязательного catch или throws. Это удобно для нарушений аргументов и инвариантов: IllegalArgumentException, IllegalStateException. Checked-исключения, например IOException, нужно обработать или объявить в throws. Throws не обрабатывает ошибку; оно передаёт обязанность вызывающему коду.

Error обычно относится к серьёзным проблемам среды. Начинающее приложение не должно ловить Throwable ради продолжения любой ценой. Обработчик выбирается по совместимости типа; более конкретные catch должны стоять перед общими.

```java
public class Example14 {
    static int readCount(String text) {
        int value = Integer.parseInt(text);
        if (value < 0) {
            throw new IllegalArgumentException("negative count");
        }
        return value;
    }

    public static void main(String[] args) {
        String text = "many";
        try {
            System.out.println(readCount(text));
        } catch (IllegalArgumentException error) {
            System.out.println("Некорректное количество");
        }
        System.out.println("Программа продолжилась");
    }
}
```

```output
Некорректное количество
Программа продолжилась
```

NumberFormatException является подклассом IllegalArgumentException, поэтому выбранный обработчик ловит ошибку преобразования. Он также ловит отрицательное число из проверки. Если для этих случаев нужны разные сообщения, обрабатывай их осознанно отдельно.

## Где обрабатывать

Нижний вычислительный метод обычно не знает, как пользователь хочет увидеть отказ. Он может бросить исключение с контекстом. Верхний слой интерфейса решает: повторить ввод, показать сообщение, прекратить команду. Не печатай и не бросай ту же ошибку на каждом слое: получатся дубли и неудобный контракт.

Пустой catch скрывает отказ. Возврат 0 из catch может выдать ошибку за законное значение. Если исключение преобразуется в другое, сохраняй исходную причину конструктором с cause. Для пользовательского сообщения не обязательно показывать весь внутренний stack trace, но для диагностики его нужно сохранить.

## Finally и ресурсы

Finally обычно выполняется при выходе из try/catch, в том числе при return и исключении. Не помещай туда return: он способен подавить предыдущий результат или ошибку. Аварийное завершение процесса и некоторые системные ситуации не дают гарантии выполнения finally.

Try-with-resources закрывает AutoCloseable-ресурсы даже при исключении. Ресурсы закрываются в обратном порядке объявления. Если одновременно ошибка возникла в теле и при закрытии, дополнительные ошибки могут быть сохранены как suppressed. Это надёжнее ручного close после чтения: до него выполнение может не дойти.

## Безопасная практика

В заданиях опасные фрагменты помещены в комментарии с пометкой «НАМЕРЕННАЯ ОШИБКА». Перенеси их в рабочую область только при изучении соответствующего отказа. Логические ошибки, не приводящие к зависанию и разрушению данных, могут выполняться. Заготовка, которая успешно стартовала, ещё не является решённой задачей.

Перед практикой прочитай stack trace небольшого опыта: найди тип исключения, сообщение и первую строку своего кода. Объясни различие throw, throws и catch. Укажи слой, который должен решить, повторять ли ввод после отказа.

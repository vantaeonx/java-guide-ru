# 17. Generics: связь типов в договоре

## Параметр типа сохраняет информацию

Generics позволяют описать алгоритм или контейнер один раз и связать типы его входов и выходов. В Box<T> буква T обозначает параметр типа, а Box<String> подставляет String. Компилятор проверяет, что туда не попало число, и знает тип результата get без ручного приведения.

Object мог бы хранить любую ссылку, но связь между «что положили» и «что достали» теряется. Ручное приведение переносит часть проверки на время выполнения. Raw type, например просто List, тоже теряет информацию и создаёт предупреждения. В курсе raw types не используются в рабочем коде.

```java
public class Example17 {
    static final class Slot<T> {
        private final T value;

        Slot(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    static <T> T chooseFirst(T first, T second) {
        return first;
    }

    public static void main(String[] args) {
        Slot<String> slot = new Slot<>("карта");
        String item = slot.get();
        System.out.println(item);
        System.out.println(chooseFirst(6, 9));
    }
}
```

```output
карта
6
```

Параметр метода `<T>` объявлен перед возвращаемым типом. Он не связан с одноимённым параметром другого класса. Ромб `<>` позволяет вывести аргумент типа конструктора из контекста. Для примитивов применяются обёртки: Slot<Integer>, а не Slot<int>.

## Инвариантность

Integer является подтипом Number, но List<Integer> не является подтипом List<Number>. Иначе через ссылку List<Number> можно было бы добавить Double в исходный список Integer. Запрет защищает обещание списка о типе элементов.

Это называется инвариантностью параметризованного типа. Массивы имеют другую модель совместимости и проверяют часть записей при выполнении; не переноси правила массивов на generics.

## Wildcard и направление данных

`List<? extends Number>` означает список некоторого неизвестного подтипа Number. Из него безопасно читать Number. Добавить произвольный Integer нельзя: фактическим списком мог быть List<Double>. Слово extends здесь не даёт право создавать новый неизвестный тип.

`List<? super Integer>` означает список некоторого супертипа Integer. В него безопасно добавить Integer, потому что это может быть List<Integer>, List<Number> или List<Object>. При чтении без дополнительной информации гарантирован только Object.

Правило PECS помогает выбрать границу: producer extends, consumer super. Это правило о потоке значений конкретной операции. Если метод и читает, и пишет строго связанный тип, нужен именованный параметр T либо конкретный тип, а не механическое применение wildcard.

## Ограничения параметров

`<T extends Number>` разрешает использовать операции, известные Number, но не произвольную арифметику `a + b` над T. Операторы Java не становятся обобщёнными операторами чисел. Можно вызвать doubleValue и сознательно принять соответствующий тип и точность результата.

Один параметр связывает несколько мест договора. Например, метод копирования принимает источник `List<? extends T>` и приёмник `List<? super T>`. Два независимых wildcard такой связи автоматически не создают.

## Стирание и пределы

Большая часть информации о параметрах generics стирается из обычного представления объектов при выполнении; компилятор вставляет необходимые проверки и приведения. Поэтому нельзя написать `new T()` или `new T[10]`, а `instanceof List<String>` не является обычной допустимой проверкой. Проверка `instanceof List<?>` возможна, но не доказывает тип всех элементов.

Не подавляй предупреждения, пока не понял, какое обещание обходишь. Перед практикой объясни запрет List<Integer> -> List<Number>, выбери extends/super для чтения и добавления и укажи, почему общий тип Object слабее связанного параметра T.
